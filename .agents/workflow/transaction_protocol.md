# 事务协议（Transaction Protocol）

## 什么是事务（Transaction）

> 事务是针对**一个连贯的工程目标**所完成的一轮完整的"决策 → 实现 → 验证"循环。

每个事务是项目推进的一个原子历史单元：它保留从问题识别到最终结果的完整决策链条。

## 事务 ID 如何分配

- 使用**顺序编号**，四位零填充：`0001`、`0002`、`0003`、……
- 新事务的 ID = 当前最大事务编号 + 1（不存在任何事务时从 `0001` 开始）
- 编号一经分配永不复用，即使某个事务被放弃

## 每个事务的目录结构

每个事务是 `transactions/` 下一个以 ID 命名的目录：

```
transactions/
└── 0001/
    ├── context.md     # 事务开始时的相关项目状态
    ├── plan.md        # 规划者的提案
    ├── review.md      # 评审者的发现
    ├── task.md        # 优化者的最终可执行任务规格说明
    ├── execution.md   # 编码者实际做了什么，包括重要的实现决策
    └── result.md      # 最终结果
```

## 各文件的用途

### context.md

记录事务开始时的相关项目状态：当时的 `project_state.md` 摘要、触发本事务的原因、相关背景。它是事务的"时间胶囊"，使历史事务脱离当前项目状态也可以被独立理解。

### plan.md

记录规划者的提案，内容要求见 `roles/planner.md`。

### review.md

记录评审者的发现，按"已确认的问题 / 可能存在的风险 / 需要验证的假设"分类，要求见 `roles/reviewer.md`。

### task.md

记录优化者的最终可执行任务规格说明，内容要求见 `roles/optimizer.md`。它是编码者实现的**唯一依据**。

### execution.md

记录编码者在实现过程中**实际做了什么**，包括：

- 实际执行的步骤
- 重要的实现决策及其理由
- 与规格说明的偏差（如有）及原因
- 遇到的问题

### result.md

记录最终结果，至少包含：

- 变更的文件
- 执行的测试 / 验证命令
- 验证结果
- 成功 / 失败
- 已知的局限
- 后续问题
- 建议的下一步

## 历史保留规则

- **事务关闭后，不应重写历史事务文件**，除非是更正明确的事实性错误（更正时应注明更正说明及日期）。
- 新的工作永远开新的事务，而不是修改旧事务。
- 后续事务需要引用历史时，通过事务 ID 引用（例如："见事务 0003 的 `result.md`"）。

## 决策历史

事务系统的目标不仅是记录改动了哪些代码，而是使以下**决策链条**始终可以被还原：

```
项目状态
   ↓
提出的决策（plan.md）
   ↓
批评意见（review.md）
   ↓
最终决策（task.md）
   ↓
实现（execution.md）
   ↓
结果（result.md）
```

这段历史应当让未来的代理或人类能够理解：重要的实现决策是**为何**做出的、当时考虑过哪些方案、某些方案为何被否决。
